# Production operations and release qualification

This repository contains a deployable application blueprint and local qualification tools. Production infrastructure has **not** been provisioned. Owning a domain, choosing providers/regions and completing independent acceptance remain prerequisites. No SLA, RPO, RTO, capacity or compliance certification is asserted.

## Local commands

- `npm run local:up`, `npm run local:verify`, `npm run local:down`: existing complete Docker development stack.
- `npm run ops:test`: signature, expiry, build-binding and artifact-tampering tests for release evidence.
- `npm run ops:restore-drill`: creates an isolated Docker PostgreSQL 17 cluster, runs governance/operations/platform tests, creates an AES-GCM encrypted custom-format dump with an Ed25519 manifest, restores to a fresh quarantine database, checks real application records and all migrations, and rejects modified ciphertext before SQL executes. The script removes its own containers/network/temp files. The local operations image remains cached.
- `node tests/operations/container-smoke.mjs`: verifies the built local API image as a non-root, read-only container with no external network, then removes it. This uses an ephemeral development database to test packaging, not production provider acceptance.
- `npm run ops:load`: bounded synthetic embedded-database bootstrap baseline. `LOAD_CONCURRENCY` (1–100) and `LOAD_REQUESTS` (1–10000) control the fixture. This measures neither production capacity nor hot-tenant/soak behavior.
- `npm run ops:preflight`: fail-closed configuration and signed-evidence validation. Missing configuration intentionally fails. It never provisions, deploys or grants launch approval.

The restore drill requires Docker and downloads/builds local images. All payloads are synthetic; production credentials must not be used. A logical dump excludes cluster roles and separately stored object/media bytes. Real deployments need managed PITR and matching independent object/media backups in addition to this test.

## Deployment blueprint

Build `deploy/Dockerfile` targets `api` and `web`. The API uses a non-root Node process with production dependencies. `deploy/compose.production.yaml` separates edge, web, API, durable workers and ClamAV. Application containers use read-only roots, dropped capabilities, secret-file inputs and private internal services. API and worker database URLs are distinct. Only Caddy exposes public ports. `/internal` metrics paths are blocked at the edge; operator access is through the private network with a bearer credential. Worker health is a process heartbeat, not a guarantee that each queue is healthy.

Supply scanned immutable image digests using `deploy/production.env.example`; do not put secrets there. The compose file references operator-created files in ignored `secrets/`. These files are an input mechanism, not a managed secret vault. Use workload identity for private S3 and a dedicated secret manager at deployment. The API and worker need independent runtime, email, model, scanner, storage and database qualification. The Eve runtime and managed database/private S3 are external prerequisites, not services silently provisioned by this compose file. Media needs its own qualified WSS/recording deployment.

Set `PUBLIC_HOST` to an owned DNS name, arrange DNS/firewall/ACME reachability, and supply `ACME_EMAIL`. Caddy's automatic HTTPS configuration is a blueprint; no DNS record or certificate has been issued. Its trusted private address is configured explicitly as `TRUSTED_PROXY_CIDRS`; untrusted forwarding headers cannot select rate-limit identities. Adjust the private subnet and trust configuration together if they conflict with your network.

Use a separate migration owner to run all migrations before application startup. Production startup refuses an owner/superuser/BYPASSRLS login and does not automatically migrate. Existing migrations are forward-only; database changes that remove data require an explicit expand/migrate/contract release with retained compatibility. Do not point application services at the migration-owner connection.

## Durable queues and overload

Existing transactional outbox/lease/retry/idempotency protocols remain the queue transport. Shared PostgreSQL rate buckets now apply across API replicas, with database-time windows, HMACed client identifiers and route isolation; database failure does not bypass the limiter. High traffic increases primary-database write load, so benchmark before selecting a separate limiter/broker.

Organization operations expose pending/dead counts and oldest event timestamps for connector/developer delivery queues. The replay endpoint accepts a recorded reason and only moves eligible dead deliveries back to pending; worker authorization rechecks still apply. Never replay uncertain tool/provider actions through this control. Their existing reconciliation protocol requires provider outcome evidence. Replay reasons are immutable operational records. Lifecycle jobs expose failed/held/storage/receipt backlogs separately. Comprehensive broker fan-out, all-queue dashboards, event retention, admission/backpressure thresholds and fleet-scale delivery receipts remain pending.

## Observability and incident handling

Each response carries a generated `x-orbit-trace-id`, also present as Fastify's request ID. Error logging is sanitized to type/code and omits arbitrary provider/SQL exception text. This is request correlation, not full distributed tracing. Add bounded, redacted OpenTelemetry spans across runtime and provider boundaries before claiming end-to-end traces.

`/internal/metrics` exposes aggregated route/status request counts and cumulative duration, with no user/IP/payload labels. Aggregation is bounded; flush failure increments a drop counter and logs a code. It is an operational signal, not a durable billing ledger. Existing billing usage remains the source for costs. `deploy/alerts.yaml` provides starting Prometheus rules; install a collector, dashboards, paging integration and an on-call owner, then test every alert. Histogram latency SLOs, queue age, budget/error/cost saturation and all-worker liveness need additional instrumentation and alert qualification.

Incident procedure: acknowledge the alert; record scope/timeline without customer content; identify the failing dependency using trace IDs and queue counts; stop new risky admissions using organization policy when appropriate; preserve uncertain provider outcomes; restore or reconcile using the runbooks below; verify customer-visible behavior; publish approved incident communication. `publish-incident.ts <reviewed-json-file>` uses an isolated `OPERATIONS_DATABASE_URL` to insert/update `{id,title,status,description}`; the application cannot publish incidents. `/status` displays only these explicit publications and never treats an empty feed as proof of uptime. No incident email/customer message is sent automatically by this command.

## Release and rollback

The quality workflow retains PostgreSQL and browser coverage and adds evidence tests. `security.yml` runs npm advisory admission and CodeQL security queries. The Expo advisory chain is now remediated and tested against actual consumers; retain advisory admission on every release. Use the pinned npm 12.2.1 for reviewed override semantics. The manual release-candidate workflow requires a reviewed Trivy image digest, scans source secrets/dependencies/container images, builds local API/web candidates and runs recovery/load qualification. It publishes no application image and deploys nothing. CodeQL, registry signing, scanner feeds, GitHub permissions, protected environments and workflow execution remain to be qualified in the actual repository.

The preflight requires public deployment configuration, pinned images, a `RELEASE_REVISION`, and `RELEASE_EVIDENCE_KEY_FILE`. Evidence envelope format is `{payload:<base64 exact JSON>,signature:<base64 Ed25519>}` with an adjacent `<envelope-path>.artifact`. Signed payload names `kind`, exact `revision`, `images` (API_IMAGE, WEB_IMAGE, EDGE_IMAGE, SCANNER_IMAGE), `result: passed`, `reviewer`, `assessedAt`, `expiresAt`, and `artifactHash`. Required kinds match BACKUP_RESTORE_EVIDENCE, FAILOVER_EVIDENCE, SECURITY_ASSESSMENT_EVIDENCE, PROVIDER_ACCEPTANCE_EVIDENCE and ACCESSIBILITY_ACCEPTANCE_EVIDENCE. Sign only after the corresponding review; the gate checks authenticity and artifact binding, not the truth of a reviewer's assertions.

After release prerequisites pass: stage on an isolated tenant/environment, migrate through an approved owner job, smoke-test auth/messages/private access/tasks/approvals/files/billing, start one candidate API and worker cohort, compare error/queue/spend indicators, then gradually expand. Record operator/revision/image digests and acceptance evidence. Canary control, automated rollout and fleet rollback are not yet implemented. On failure, stop candidate admissions and worker leases, fence old/outbound work, restore previous compatible images, and reconcile uncertain effects before reopening. Do not automatically down-migrate or replay billed actions. If the old image cannot read the new schema, hold traffic and perform a reviewed forward repair or quarantined restore.

## Backup, recovery, expiry and failover

Backup operator inputs: BACKUP_DATABASE_URL, canonical 32-byte BACKUP_ENCRYPTION_KEY, Ed25519 BACKUP_SIGNING_KEY_FILE, DEPLOYMENT_REGION and BACKUP_RETENTION_DAYS (1–365). Run `node scripts/operations/backup.mjs <private-output-directory>` using PostgreSQL clients. Credentials travel through environment/file inputs, never argv. Dump output streams into authenticated ciphertext; manifests and signatures are private files. The timestamp is an expiry commitment, not an automatic remote deletion operation. Register each backup/object/media copy in an independently maintained inventory and run verified expiry jobs; the database inventory table alone does not perform deletion.

Restore: set RESTORE_DATABASE_URL, BACKUP_ENCRYPTION_KEY and BACKUP_VERIFY_KEY_FILE, then run `node scripts/operations/restore.mjs <manifest-path>`. Only an empty `orbit_restore_*` target is accepted. Manifest signature, ciphertext hash and full GCM authentication are checked before `pg_restore`; plaintext exists only in a private temporary directory and is removed afterward. The command never activates the target. Only restore backups signed by a trusted operator; authenticated archives may still contain executable database definitions from that operator.

Before activation, compare current signed audit anchors; replay post-backup deletion/tombstone requests and legal holds; verify revoked memberships, credentials and sessions; disable live side-effect dispatch; reconcile runtime/provider/invoice state; restore and scan file/media bytes; measure integrity and customer workflow tests; record achieved RPO/RTO; then obtain deployment-specific recovery acceptance. Automated deletion-journal replay and PITR orchestration are not implemented.

Failover drill remains pending: create a separately fenced standby in the allowed region, verify replication lag and secret/key availability, suspend/fence the old primary and provider dispatch, promote once, validate tenant/auth/deletion state, reconcile leased or uncertain work, then route traffic through the owned TLS domain. Test database/network failure during billing, tool dispatch and checkpoint recovery. Never operate both primaries as active writers. Record measured loss/recovery times and a failback plan; no regional HA guarantee is justified by a local dump round trip.
