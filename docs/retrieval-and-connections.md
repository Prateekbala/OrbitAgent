# Retrieval, memory and connections

Implemented code lives in `apps/api/src/retrieval`, `apps/api/src/connections` and their route modules. Migrations 049–061 extend the existing PostgreSQL/PGlite store. The web UI exposes evidence retrieval in Search, retained memory in Agents, and connections in Settings.

## Retrieval and evidence

`POST /v1/search/retrieve` accepts `q`, optional `kinds`, `limit` (1–50), and `semantic`. Supported kinds are `message`, `knowledge`, `task`, `file`, `document`, `transcript`, and `memory`. Existing advanced message/page search retains its phrase, author, conversation, date, attachment and history filters.

The index uses normalized Unicode words, ICU segmentation, PostgreSQL `simple` lexical terms, overlapping code-point chunks and GIN indexes. It preserves non-Latin text and does not assume English stemming. Cross-language semantic quality depends on the operator-selected embedding model. Unknown source language is `und`; no language is fabricated.

Every indexed row and chunk has forced tenant RLS and a current source policy. Source version, private group history floor, file scan/attachment status, page provenance, explicit connection resource grants, memory boundaries, expiry, current account authority, and agent credential conversation restrictions gate candidate hydration. Stale index revisions are hidden even before a worker catches up. Embedding input and final results receive additional current-access/version checks. An authority change during inference rejects publication.

`POST /v1/search/answer` defaults to an **extractive** answer with numbered citations. Explicit `answerMode: "model"` uses an operator-configured `RETRIEVAL_ANSWER_MODEL`. Only authorized excerpts are supplied, with at most 12 sources and a 24 KB serialized evidence payload. One tool-free call has a 30-second deadline, no retries and at most 2,200 output tokens. Every generated claim requires exact supporting quotes and known citation labels. Invalid citations/quotes fail closed. Server freshness/conflict flags cannot be cleared by model output; model-reported missing evidence/conflicts can only add flags. Quote membership is checked; semantic entailment remains unverified and the UI labels model-written interpretations for source review. Current context/source authority is checked again immediately before publication. UTC daily reservations allow at most 100 attempts/workspace and 40/member, with two concurrent calls. Failed and uncertain attempts consume allowance; metadata is retained for 30 days without query, source text or generated answers. No evidence means no model call. `GET /v1/search/sources/:kind/:id?version=N&offset=N` inspects authorized source text in 10,000-character pages; a changed source requires new retrieval.

Retrieval contexts store references, not duplicated excerpts. They are bound to member, credential, workspace authority epoch, account authentication version, organization policy and a ten-minute TTL. Reuse verifies current source versions/access. Authority triggers invalidate contexts and send content-free realtime invalidations. Bootstrap exposes the authority epoch so clients also clear stale views after a missed event. Search context checks and memory refreshes bound expiry handling in open views. No new private browser persistent cache was introduced.

The ranking path considers at most 300 authorized chunks and reports candidate saturation. Semantic ranking uses finite, dimension-checked real vectors with cosine similarity; it does not substitute hashed keyword vectors for embeddings. Cold interactive semantic retrieval sends at most 32 authorized chunks plus the query. Indexed vectors can be reused only for the same embedding model. This portable exact-vector implementation requires no pgvector extension or separate search service; its candidate cap is a recall limitation, not a scale claim.

## Jobs, extraction and maintenance

The retrieval worker batches per tenant. Source-change jobs handle individual removals; the full orphan backstop is coordinated across workers once per minute so rebuilding does not rescan the growing index after every 20 documents. RLS hides unavailable sources immediately, independent of physical cleanup. Durable jobs have generation numbers, leases, retries, dead letters and atomic index replacement; stale workers cannot overwrite a newer source generation. Source expiry and deletion remove index content. `POST /v1/search/rebuild` and `GET /v1/search/health` require a workspace administrator and expose queue age, per-kind document freshness and latency aggregates without search text.

`POST /v1/search/embeddings` queues up to 20 cited source references. Each job captures actor, credential, source revision, account/policy authority, audience epoch and model. The embedding worker rehydrates through runtime RLS, processes bounded batches, rechecks authority after inference, and fences vector writes. Revoked/expired credentials and changed sources fail closed. Requeue and rebuild preserve these checks.

`POST /v1/search/files/:id/extract` reads an attached, scan-approved file through private storage. It limits input to 4 MiB, enforces a read deadline, and rechecks source access before provider input and persistence. UTF-8 text is extracted locally. Optional provider OCR handles PDF, PNG, JPEG and WebP with a bounded output and no tools. Incomplete output is rejected. Extraction revisions invalidate old chunks and derived references. Production continues to require the existing malware scanner; development-only scan bypass is labelled separately.

`POST /v1/search/transcripts` imports a retained transcript with an explicit consent reference, conversation audience, language, expiry and idempotent client ID. This is retained transcript ingestion, not a call recording service. Owners can erase transcripts; expiry purges source bodies.

Configure `RETRIEVAL_EMBEDDING_MODEL` and, independently, `RETRIEVAL_OCR_MODEL` to explicitly select real AI Gateway models. Embedding, OCR and answer models are disabled by default. They use workload identity or `AI_GATEWAY_API_KEY` on the server. Provider keys, connection secrets and OAuth tokens never enter model input, source snippets or action traces. Configure and qualify provider retention, residency, supported media, model quality and operating budgets before live use.

## Inspectable memory and declassification

`/v1/memory` lists or creates agent memories with private, conversation or workspace boundaries. The human owner supplies exact cited source revisions and an expiry within 365 days. Private entries require the owner or associated agent, plus every source audience. A workspace boundary is not an access grant to private sources.

Provenance is bounded to eight levels and 128 reference paths, with transitive cycle rejection. Corrections are optimistic, attributed revisions with a reason; they cannot silently erase source provenance. Export rechecks current authority and source lineage and bounds history to the latest 100 revisions. Deletion physically erases the selected memory and its correction history. Derived copies immediately become unavailable when their source disappears; maintenance physically purges copies whose evidence was deleted or expired. Changed source revisions remain available for authorized correction rather than being silently rewritten. Expired source versions remain inspectable only where current source access allows correction, and are excluded from reusable retrieval evidence.

`POST /v1/memory/:id/forward` creates a conversation copy that still cites the original memory. Destination membership alone never grants the original private audience.

Declassification is a separate, explicit operation with an audience acknowledgement and reason. The direct `/declassify` fast path requires the approving human to own the memory and **every transitive source**. The release records source revision, destination, published copy, approver and body hash. Its evidence is immutable and may only be revoked. Released content cannot be edited under an old approval. Source correction, deletion, expiry or release revocation invalidates the copy. Mixed-owner declassification uses a separate consent workflow described below.

### Mixed-owner consent protocol

`POST /v1/memory/:id/release-requests` snapshots an owned memory revision, title/body fingerprints, transitive source revisions and direct owners, destination, requester authentication version, policy version and audience epoch. Provenance is bounded so the published copy also fits eight levels and 128 reference paths. Ownerless, stale or inactive-owner evidence fails closed. Requests expire after 24 hours (or earlier source expiry); at most 20 pending requests per requester are admitted.

`/v1/memory-release-requests` is an audience-restricted, paginated inbox. Each owner sees only their own source references, the destination, reason and composed-memory fingerprint. Another owner's private excerpts or the composed memory are not disclosed for approval. Source inspection uses the existing current-access endpoint. An approver must retain verified human membership, source ownership, knowledge permission and destination access for conversation releases.

`POST /:id/decision` records an explicit approved/rejected decision bound to the body fingerprint and audience acknowledgement. The requester also approves their own sources. Administrators cannot substitute for another owner. Rejection is final; any owner can withdraw their approval, including after publication. `POST /:id/publish` atomically rechecks every owner, exact source version/owner set, account/policy authority, request deadline and audience epoch before creating an immutable release and copy. Repeating publication returns the existing copy. Withdrawal, ownership/account changes and source correction/deletion/expiry invalidate the release. Withdrawal immediately invalidates reusable contexts and broadcasts a content-free invalidation. A fresh request is required after audience changes; approvals are never silently carried forward.

Existing hosted-run recovery and tool execution now fence reused context by the retrieval authority epoch. Fresh dispatch can prepare fresh context; old sessions/checkpoints cannot silently resume after access changes. Existing account, source, policy and tool checks remain in force.

## Connections and supported read operations

`/v1/connections` manages personal or workspace connections. Every connection has an explicit verified human owner, independently encrypted credential record, version, health metadata and credential expiry. Consumers receive exact resource IDs and read operations with expiry; wildcard grants are rejected. Personal connections cannot grant other consumers. Source import requires the owner and fixes the resource audience. Subsequent reads recheck current owner/account/organization authority and grants.

The catalog contains bounded read adapters for all 24 entries:

- GitHub issues; GitLab issues; Linear issues; Jira issues; Sentry issues.
- Honeycomb board definitions; Vercel deployment status; Datadog monitor definitions.
- Notion paginated/nested block text; Google document plain-text export; Microsoft 365 item metadata.
- Granola notes/transcripts; Fathom recording transcripts; Fireflies transcripts.
- HubSpot contacts; Attio records; Stripe customer details; Ramp transactions.
- Shopify product descriptions; Zendesk ticket descriptions.
- PostHog insights; Hex project metadata; approved Supabase rows; named database read proxies.

These are **operation-level implementations, not complete provider coverage**. Each manifest declares exact operations, resource format, authentication, minimum provider permission descriptions (including OAuth scope identifiers where applicable), local rate cap, approval boundary, idempotency/reconciliation behavior, attribution, configuration and limitations. Notion traversal preserves reading order within 20 provider requests, 1,000 blocks, eight levels and 1 MB, with pacing, repeated-cursor/cycle rejection and current authority before every fetch. Larger trees fail closed. Embedded binaries and database rows are outside the block-text operation. Microsoft binary/Office document bodies, arbitrary provider queries, self-hosted/provider-region variants and additional resource types remain outside these bounded operations. Existing approved action adapters remain the path for separately qualified external writes; catalog reads do not bypass tool approval.

Shopify and Zendesk require an account subdomain. Datadog uses credential JSON with `apiKey` and `applicationKey`. Supabase uses credential JSON with a publishable `apiKey` and delegated authenticated-user `accessToken`, plus an explicit project, table and nonsensitive column allowlist. Service-role and secret keys are rejected. The database connector accepts only a configured named-query HTTPS read proxy on `CONNECTOR_DATABASE_HOSTS`: `GET <endpoint>/queries/<name>/records/<id>` returns `{ "title": "...", "body": "..." }`. It accepts neither raw SQL nor a database password/DSN. The proxy must independently enforce a read-only database identity, parameter binding, row/column grants and execution limits.

Outbound reads use fixed provider routes, DNS public-address validation, a pinned transport address, no redirects, deadlines and bounded response bodies. Only selected content fields are retained. Credentials stay encrypted at rest, are accessed only inside the provider boundary, and are never returned to consumers. A configured credential alone does not perform a health probe or establish provider coverage. Successful imports update health; auth failures require reconnect, and rate limits respect bounded Retry-After backoff. Revocation erases credentials, disables hooks, removes imported content and invalidates reusable context. Member suspension/restriction also revokes owned connections and consumer grants; credentials do not transfer implicitly during offboarding.

Google Drive, Linear, GitHub, GitLab, Jira, Microsoft 365, Notion and HubSpot have session-bound, single-use OAuth consent. PKCE is used by the five documented supporting profiles; Jira, Notion and HubSpot use their documented confidential-client flows. Notion uses HTTP Basic client authentication. Fixed endpoints, bounded responses, returned-scope checks and encrypted verifiers/tokens stay server-side. Denial consumes state without token exchange. Owners select local read-only or write access. GitHub OAuth requires broad repo permissions even for private reads; local read-only mode still blocks native writes. Google writes request drive.file, so the remote file must also have been authorized for that provider app. Notion provider capabilities are configured on the registered application. Callback persistence rechecks account/policy authority. Reconnects are connection-version fenced and keep the same record while revoking old consumer grants, disabling hooks and erasing old imports, because the provider account may have changed. Refresh leases and generations fence token rotation/revocation. Configure the matching `CONNECTOR_GOOGLE/LINEAR/GITHUB/GITLAB/JIRA/MICROSOFT/NOTION/HUBSPOT_CLIENT_ID` and `_CLIENT_SECRET`; callbacks are `<WEB_ORIGIN>/api/v1/connections/oauth/<provider>/callback`. Remaining providers accept explicitly owned tokens; no additional OAuth client is claimed.

## Native approved writes

Native updates use the existing hosted `connection_action` tool, approval digest, policy rules, single-use execution capability and durable `tool_actions` ledger. Owners explicitly enable writes at connection creation, token rotation or OAuth reconsent. Existing connections migrate as read-only. Exact operation/resource grants are required for both requester and agent (an owning requester has implicit owner authority). Local read imports cannot invoke a write operation.

Implemented native operations are GitHub issue title/body/state; GitLab and Linear issue title/description; Jira issue summary; Google Drive file name/description; Microsoft 365 file rename; HubSpot contact first/last name; Stripe customer description; and Notion plain paragraph text replacement. Payment, arbitrary code/query, access changes, destructive deletion and unspecified fields are not accepted by these operations. Notion replacement rejects formatted/linked/mention paragraphs rather than silently discarding formatting.

Use `{ "resource": "acme/repository/7", "patch": { "title": "Reviewed title" }, "expected": { "title": "Previous title" } }` as the JSON payload string for `issue.update`. Every patched field requires its reviewed previous value. The manifest lists provider-specific operations and allowed fields. Execution reads current fields, rejects changed preconditions, rechecks run/approval/account/grants before every request and confirms the resulting fields. Provider ETags are sent for Google/Microsoft when supplied; other providers do not promise atomic compare-and-set. Stripe receives a stable provider idempotency key. Up to three requests are reserved against a six-second local provider allowance; larger Notion imports reserve 20 requests and pace traversal. Provider rate-limit backoff and reconnect health are retained.

A committed timeout remains `outcome_unknown`. Reconciliation performs read-only postcondition checks, never another mutation. Confirmed postconditions are labelled as such by their receipt; they do not claim which actor last changed the provider. A mismatching postcondition does not prove non-application and remains unknown. The existing evidence-based administrator reconciliation endpoint remains available. Credentials and raw provider responses never enter proposals, receipts, model input or traces.

## Signed events and email-to-channel

`PUT /v1/connections/:id/webhook` creates/rotates independent incoming and outgoing secrets and explicitly selects event subscriptions. The returned secrets are shown only to the configuring owner. `CONNECTOR_WEBHOOK_HOSTS` is an exact public HTTPS destination allowlist.

The inbound protocol is **orbit-bridge-v1**, not a claim to implement every vendor's native webhook signature scheme. A trusted bridge must verify the provider's native authenticity before translating an event. Post exact UTF-8 JSON to the returned path with `x-orbit-timestamp` (Unix seconds) and `x-orbit-signature` (hex HMAC-SHA256 of `<timestamp>.<exact-body>`). The replay window is five minutes. Event IDs are deduplicated with a payload hash; reusing an ID for a different event is rejected, including after email body redaction.

Accepted subscribed events are `resource.changed`, `resource.deleted` and configured `email.received`. Changed events can refetch only an already imported resource and preserve its original retention ceiling. Incoming events never grant a new resource. Jobs claim one lease immediately before processing, recheck the lease before provider reads and before retaining refresh results, and fence completion. They have bounded retries, expiry, completion tracking and dead-letter inspection/retry endpoints. Outbound notifications contain IDs and completion status, never provider document bodies, and carry stable idempotency IDs plus the existing `x-orbit-id/timestamp/signature` signing contract. Receivers must deduplicate retries.

An email route requires an active channel, exact allowed sender addresses and trusted bridge attestation of `dkim-pass`. The bridge is responsible for validating the actual upstream email authentication; an unsigned From header is never sufficient. Email is posted through a separate restricted service identity, not impersonated as the connection owner, and cannot wake agents through human-mention dispatch. Completed email event bodies are redacted. This does not provision a live inbound email address or send real email.

### Native signed provider events

GitHub, GitLab, Linear and Stripe have independent native signature adapters at `/v1/connection-native-events/:workspace/:connection`. Owners configure `/v1/connections/:id/native-webhook` and complete registration in the provider's settings; this does not claim automatic remote subscription provisioning. GitHub uses a generated, one-time displayed secret. GitLab uses its Standard Webhooks `whsec_` signing token, never the legacy plain secret header. Linear verifies the signed body's millisecond timestamp; Stripe verifies timestamped v1 signatures, including rotation headers. Exact signed bytes are verified before parsing, and only resource IDs/operations plus a payload hash are retained. Delivery IDs are namespaced by provider and deduplicated against exact bytes. Signed payload hashes are also unique per hook generation, so substituting an unsigned GitHub/Linear delivery-ID header cannot enqueue a replay.

Only already imported, unexpired resources can enter the native queue. Jobs capture hook generation and recheck subscription, owner and hook authority during refresh and completion. Native deletion is confirmed by a current provider 404; a delayed delete event for an existing object refreshes it and retries confirmation without erasure; unresolved absence can dead-letter. A newer concurrent import is protected from deletion. Connection revoke/rotation/reconnect and hook expiry erase/disable native signing credentials. GitHub has no signed delivery timestamp, so its generated keys expire within the 30-day deduplication retention and cannot be reused through this API. Configure fresh keys in the provider on rotation. Native webhook registration and callback deployment still require independent provider-account qualification.

## Verification and qualification

`npm run search:evaluate` creates and destroys an isolated synthetic database, indexes a configurable 100–10,000 documents, and reports recall@5, reciprocal rank, indexing throughput and p50/p95 retrieval latency. Set `RETRIEVAL_EVALUATION_DOCUMENTS` for corpus size; `TEST_DATABASE_URL` selects disposable PostgreSQL databases instead of embedded PGlite. No model inference occurs by default. `RETRIEVAL_EVALUATION_CONCURRENCY=1..8` measures concurrent retrieval and throughput. Optional `RETRIEVAL_EVALUATION_EMBEDDING_MODEL` plus explicit `RETRIEVAL_EVALUATION_ALLOW_INFERENCE=true` enables a small synthetic cross-language semantic smoke test; it may incur provider inference charges and was not run during local verification. Initial multilingual lexical cases use Latin, full-width Latin, accented text, Devanagari and Japanese. This is a repeatable baseline, not production semantic quality or multi-tenant capacity qualification.

API tests cover forced RLS, stale source/index revisions, private history, revocation, memory release provenance, extraction limits, credential secrecy, OAuth session/replay/refresh, provider-specific request fixtures, event deduplication, service-identity email and fenced delivery. Browser tests cover evidence inspection, memory correction/deletion and settings-to-import-to-search. CI automatically includes these suites.

Every catalog entry remains `unvalidated` for live provider use. Connection validation records distinguish `fixture` and owner-attested `provider_test` evidence; they do not turn a successful credential configuration into full connector coverage. Independently validate each operation, scope, pagination/limits, native event translation, OAuth refresh, revocation, failure recovery and attribution in provider test accounts before enabling live production use. Per user instruction, live-provider validation remains pending. No provider accounts, external model calls, paid resources or production deployment were provisioned for this implementation.

## Recorded local verification

The completed serial regression run passed all 397 PostgreSQL API tests and all 59 Chromium browser tests. Six affected browser flows passed again after the final named-audience accessibility refinement. The embedded run passed 393 tests with four PostgreSQL-only tests skipped. Type checks, formatting, the production web build and managed-runtime compilation also passed; the production dependency audit reported no vulnerabilities. These are local results; CI execution and live provider qualification are separate checks.

The synthetic PostgreSQL baseline on 5,008 documents and 24 multilingual lexical queries returned recall@5 and mean reciprocal rank of 1.0. Before query-plan tuning, p95 was 2,229 ms; the tenant/principal-bound ID selector plus runtime-RLS hydration reduced measured p95 to 21 ms (p50 13 ms). Indexing took 30.8 seconds in that run. These measurements used local disposable PostgreSQL while other verification work was active; they are not production throughput, concurrency, semantic-quality or provider-coverage guarantees. The reproducible CI baseline remains the acceptance mechanism.

The existing local store was backed up before applying migrations, with its core row counts preserved. New tables force tenant RLS. Project services remain stopped; test servers and the disposable PostgreSQL container are cleaned up after verification. No live email, provider account, model inference or deployment is required to run the fixture suites.

The current eight-client PostgreSQL run on 10,008 synthetic documents recorded recall@5/MRR of 1.0 and p95 retrieval latency of 28 ms (p50 10 ms). Coordinating the orphan backstop reduced indexing time from 90.5 seconds to 30.0 seconds in consecutive local runs. These are controlled synthetic measurements, not fleet or production corpus qualification.
