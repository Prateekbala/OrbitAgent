# Migration, synchronization, shared channels and exports

Migration management and shared channels are available from the workspace sidebar. They use the existing PostgreSQL tenant boundary, file upload/scanning pipeline, message history intervals, transactional outbox, retrieval invalidation and execution authorization checks. Applied database migrations are 066 and 067.

## Import lifecycle

1. A verified human workspace administrator creates a paused source, identifying its provider and original workspace. A UUID client ID makes creation retry-safe. The same provider/workspace cannot be registered twice in a tenant.
2. Map each original channel to a target channel. The operator explicitly attests source authorization and reviews the destination audience. Private history and public destinations require an explicit audience acknowledgement. Channel mappings become fixed once history exists. The API never creates accounts, matches email addresses, or grants membership based on an export.
3. Map original identity IDs to existing active memberships, or keep external attribution. A display-name match is not identity verification. Original author ID/name, provider, workspace, channel/message IDs, creation time, source revision, reaction counts and known reaction authors remain inspectable. A local author foreign key never pretends that an unmapped external author signed in.
4. Stage bounded batches using stable UUID client IDs. Native provider pages can be normalized using `/v1/migration-normalize`. A source message/revision is unique, and reusing that revision for different content is rejected. At most 100 records are accepted per batch within the 400 KB API body limit; split large pages. At most 10,000 pending/conflicted records and 100 sources per workspace bound admission.
5. Run preflight to inspect actual target audiences, missing channel/thread mappings, archived destinations and agreed retention conflicts. Staging and preflight do not publish messages, notify recipients, execute tools, or wake agents. The report identifies unmapped identities, unsupported content and missing file bodies. A provider export cannot prove that unexported history exists or that the operator is authorized to declassify it.
6. Start the source. The bounded worker commits each processed batch with message changes, origin maps, audit events and its checkpoint. Restarting or competing workers cannot duplicate imported messages. Pause fences further work; disconnect also erases relay credentials and cancels pending outbound deliveries. Access/authentication/policy changes pause background processing until the owner reviews and resumes authorization.

Roots are admitted before replies. Missing roots stay pending and are reported. Threads are constrained to an actual root in the mapped channel. Imported history uses append-only local sequence positions with original timestamps: later backfill never rewrites existing read cursors. Ordering within newly staged history is deterministic; it is not a retroactive resequencing of a live channel.

Source-owned content requires explicit migration controls for edits. Local ownership keeps inbound revisions for review. Manual ownership applies a newer revision only while its local version remains unchanged; otherwise an operator chooses source, local, or explicit omission. Stale chronological provider revisions cannot overwrite newer ones. Opaque revision ordering requires review. Deletions create normal tombstones, fence source-linked inbox work, invalidate derived retrieval state, and remove retained files through the cleanup pipeline. Deleted imported bodies are scrubbed from staged payloads while their immutable fingerprints remain available for deduplication.

## Provider capability and validation boundaries

The supported provider set is Slack, Microsoft Teams and Discord. Buzz is excluded at the user's request.

- **Slack:** exported/history message objects, original authors/timestamps, root/reply IDs, edits, reaction counts and known users, and file references. `HistoryProviders.slack` uses separate `conversations.history` and `conversations.replies` endpoints with conservative pages and explicit rate-limit backpressure. Slack reaction author lists can be incomplete; retained counts are not fabricated from the known list. Blocks have inert text fallbacks; unsupported subtypes are reported.
- **Teams:** Microsoft Graph channel message and reply pages, original identities/times/revisions, attributed reactions and attachment references. HTML becomes inert text, with a reported formatting/card/hosted-content limitation. Pagination is bound to the exact Graph channel/reply path and origin; foreign URLs and redirects are rejected. Thread reply collection is separate from root collection. Delta endpoint coverage is not assumed from a message export.
- **Discord:** bot-authorized message pages, snowflake pagination, original identities/times, attachments and aggregate reactions. Ordinary reply references are preserved as reported references, not incorrectly converted into threads. Collect actual thread channels with an explicit reviewed root mapping. Missing MESSAGE_CONTENT authorization is reported; reaction users are never invented from aggregate counts.

Native read transports use fixed HTTPS origins, bounded responses/deadlines, no redirects, and no automatic network retries. Each has an independent transport/normalization test. Deployment credentials, scopes, private-resource access, plan limits, live completeness, native outbound provider effects and reconnect/long-running collector behavior still require provider-account acceptance tests. Local fixture success is not live provider qualification.

Source file URLs are never fetched implicitly. Upload retained binaries through the normal quota/scanning pipeline and supply `fileId` alongside the original file ID in a normalized record. Only clean, owner-uploaded files in the target channel can be mapped. Mappings persist across subsequent complete source revisions; replacement/removal uses the existing cleanup lifecycle. Missing, inaccessible, or unsupported bodies remain visible omissions, never successful binary migrations.

The browser accepts native arrays and normalized pages. `examples/migrations/slack-archive.ts` converts authorized, already extracted `channels.json`, `users.json` and daily channel JSON into stable NDJSON batches; it refuses paths escaping the selected directory and oversized source files. `send-batches.ts` delivers those batches to a configured inbound relay source. These examples do not extract arbitrary ZIPs or follow private download links.

Provider references: [Slack export format](https://slack.com/help/articles/220556107-How-to-read-Slack-data-exports), [Slack history](https://docs.slack.dev/reference/methods/conversations.history/), [Slack replies](https://docs.slack.dev/reference/methods/conversations.replies/), [Microsoft Graph chat messages](https://learn.microsoft.com/en-us/graph/api/resources/chatmessage?view=graph-rest-1.0), [Discord message resource](https://github.com/discord/discord-api-docs/blob/main/developers/resources/message.mdx).

## Live synchronization protocol

The platform supports inbound and bidirectional sources through an operator-run, provider-authorized relay. Deploying a provider collector is an explicit operator action; creating a source does not provision a provider app or start a collector. Provider credentials stay in that relay, outside model input and Orbit traces. The native read transport library and signing examples are provided to implement collection using registered provider applications.

The source owner rotates a one-time relay secret. Resuming after an owner authentication or organization-policy revision clears the old secret; a fresh authorized rotation is required. It is encrypted at rest with source-bound AAD. Every relay request includes:

- `x-orbit-workspace`: the target workspace UUID.
- `x-orbit-timestamp`: current Unix milliseconds, accepted within five minutes.
- `x-orbit-signature`: `v1=` plus the hex HMAC-SHA256 of `timestamp + "\n" + METHOD + "\n" + path + "\n" + canonicalJson(body)`.

Canonical JSON sorts object keys recursively and preserves array order. Use the supplied signing helper. Serve the API over HTTPS outside literal loopback. Never place relay/provider secrets in URLs, source files, chat or model context.

`POST /v1/migration-relay/:id/batches` accepts stable, deduplicated batches. Paused connected sources buffer inbound pages while history is reviewed; only active sources apply them. Provider collectors must persist their channel and reply cursors and periodically refetch/reconcile changed history. A signed webhook ingress is not proof that every original provider event was delivered. The completeness report exposes applied checkpoints and deterministic SHA-256 per-channel origin/revision checksums.

`POST .../claim` accepts `{clientId}` and returns at most one outbound delivery with a 60-second fencing token, current message version, mandatory attribution, external origin/receipt IDs, retained file metadata and reactions. A claim client ID cannot claim another action on retry. Ordinary member messages can enqueue delivery, but only the currently authorized consenting source owner can drive the relay. Private access, archive status, current version and source authority are rechecked before disclosing content. Imported changes do not echo; returning provider events can carry `echoActionId` to suppress the originating action. Importing a different source or external organization's message never silently forwards it into another connection.

`POST .../complete` requires the unexpired lease token, provider message ID and a confirmed `completed` or `uncertain` result. Lost responses, expired leases, pause, disconnect or secret rotation never automatically replay a write. Delivery inspection and explicit reconciliation require a current owner browser session. Retrying an uncertain delivery requires provider-confirmed non-execution, evidence and fewer than five attempts. A configured provider token is not proof that an external effect completed.

## Shared channels across organizations

A shared channel has one owning workspace and remains private. A host workspace and organization administrator invites another organization using a short-lived, hashed token and explicit proposed policy. The receiving organization administrator reviews the exact terms and selects verified active participants from a receiving workspace in the agreed region. Source organization authentication/domain policies and host MFA/SSO/region compatibility are enforced. Organization policy revisions invalidate grants until fresh consent. No external identity is silently enrolled in the host organization.

External participants receive channel-scoped shadow guest identities, linked to their actual source membership, account authority and organization. They continue using their original workspace session. A narrow bridge exposes authorized messaging, threads, editing/deletion, reactions, read receipts, files and governed channel exports. It issues no general host-workspace session or cross-tenant API key. Host messages visibly identify external organizations; ordinary host conversation URLs remain inaccessible from the external workspace.

History is either retained or starts at admission, using the existing membership interval boundary. Participants must agree to identical retention, export, recording and agent terms. Recording is explicitly disabled; this feature does not claim that calls/recording have been built. Agent permission governs host agents; external participants cannot grant or run agents in the host workspace.

Accepted channel restrictions remain durable after organization revocation. Existing accepted terms cannot be relaxed by deleting a grant or issuing a replacement invitation; use a new channel for different terms. PostgreSQL immediately hides history outside retention, and the bounded retention worker tombstones expired bodies and queues file cleanup. Retention is not a claim of immediate erasure from existing operational backups, which remains governed by the broader data lifecycle work.

Either organization's administrator can revoke participation. Participant changes/revocation close membership intervals and invalidate reusable retrieval contexts. PostgreSQL rechecks source membership, organization membership, account authentication version, source read permission and both organization policy revisions during content access. Source offboarding therefore fences a previously admitted external identity even before a cleanup job runs. Shared activity events sent to the receiving workspace contain only a grant ID and the explicit recipient; they never include another workspace's message body or channel inventory.

## Readable exports

`GET /v1/workspace-export` streams a POSIX tar archive with readable Markdown, JSON, stable IDs, original attribution, timestamps, threads, reactions, retained file binaries and SHA-256 metadata, followed by `manifest.json`. Files pass through existing authorization/storage checks and are verified as they stream. A source/account/permission revocation aborts delivery; discard any incomplete archive.

Exports include only currently accessible conversations and their related tasks, comments, projects and eligible knowledge. Page export governance still applies: only current approved, unblocked, fresh versions with visible lineage and eligible ownership are exported. Historical/private/credential data is not silently included; the manifest describes omissions. Shared export prohibitions apply to workspace exports as well as the separately authorized full shared-channel archive.

Exports are paginated internally and streamed without creating public object links or collecting workspace/file bodies in memory. They are explicitly live and access-checked, rather than point-in-time database backups. Existing messages are emitted in stable-ID pages; original timestamps and local sequence values allow a reader to reconstruct chronology. Operational backups, private drafts/memories, credentials and inaccessible history are outside this readable export format.
